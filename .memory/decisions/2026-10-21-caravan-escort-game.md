# Decisions: 마차 호위 중세 판타지 게임 - 공주를 구했다?!

- Date: 2026-10-21
- Status: Confirmed

## D01. 게임 형태와 지원 환경
- **Chosen**: React 기반 데스크톱 브라우저 게임. 1인 플레이로 시작하며 모바일과 협동 플레이는 첫 버전 범위에 포함하지 않는다.
- **Rationale**: 한 명이 마차를 호위하는 핵심 플레이를 먼저 완성한다.

## D02. 게임 렌더링 구조와 분위기
- **Chosen**: React 웹앱 안에 Phaser 게임 화면을 두고, 메뉴·로그인·기록 UI는 React가 담당한다. 게임은 중세 판타지 픽셀 아트풍으로 표현한다.
- **Rationale**: 실시간 전투와 충돌은 게임 엔진에 맡기고 계정·메뉴 화면은 React 구조에 둔다.

## D03. 첫 버전 플레이 범위와 조작
- **Chosen**: 목적지까지 약 15분 동안 마차를 호위하는 첫 챕터를 완성한다. WASD와 방향키로 이동하며, 플레이어는 화면 안에서 자유롭게 움직인다. 공격은 자동 발동한다.
- **Rationale**: 생존형 액션의 이동·성장에 집중하고, 요청된 첫 챕터의 시작과 결말을 모두 경험할 수 있게 한다.

## D04. 스테이지 흐름과 배경 전환
- **Chosen**: 마왕성에서 시작한다. 첫 준보스 전 용암지대를 거쳐, 두 번째 준보스 전 초원·마을 지대로 이동한다. 각 준보스 등장 약 30초 전부터 배경을 서서히 전환한다.
- **Rationale**: 마왕에게서 공주를 구하러 가는 여정을 배경 변화로 보여준다.

## D05. 이벤트 및 시간표
- **Chosen**: 이벤트는 3·6·9·12분에 발생한다. 이벤트 선택 중 게임은 일시 정지하고, 상황 설명과 Yes/No 두 선택지만 보여준다. 각 선택의 카르마·보상 효과는 이벤트 맥락에 따라 정한다.
- **Rationale**: 짧고 이해하기 쉬운 선택을 유지하면서 선악 선택을 단순한 Yes/No 규칙에 고정하지 않는다.

## D06. 준보스·보스전 동작
- **Chosen**: 준보스는 5·10분, 최종 보스는 15분에 등장한다. 전투는 계속되지만 게임 진행 타이머와 일반 몬스터 생성은 보스전 중 멈춘다. 준보스전에서는 이미 나온 일반 몬스터가 남고, 최종 보스전 시작 시에는 사라진다. 준보스를 처치하면 타이머와 일반 몬스터 생성을 재개한다. 보스전은 이후 별도 전투 화면으로 바꿀 수 있도록 한다.
- **Rationale**: 준보스전은 기존 호위 전투와 이어지게 하고, 최종전은 집중할 수 있게 정리한다.

## D07. 플레이어와 마차의 생존 규칙
- **Chosen**: 몬스터는 플레이어와 마차 중 가까운 대상을 공격한다. 일부 저체력 특수 몬스터는 마차를 우선 공격한다. 마차 내구도가 0이면 패배한다. 플레이어는 쓰러진 뒤 잠시 후 마차 근처에서 일시 무적 상태로 부활한다.
- **Rationale**: 플레이어 생존보다 마차 보호를 핵심 목표로 삼는다.

## D08. 카르마와 외형 변화
- **Chosen**: 카르마는 -100~+100, 시작값은 0이다. -50 이하 악, -49~+49 중립, +50 이상 선으로 분기한다. 현재 카르마가 악 구간에 들어가면 용사의 외형을 검정·보라색 중심의 흑화 스프라이트로 바꾼다. 외형은 현재 수치를 따르고 최종 보스·엔딩은 판 종료 시점 수치로 정한다.
- **Rationale**: 이벤트 선택으로 바뀐 선악 성향이 플레이와 결말에 드러나면서 선택을 되돌릴 여지도 남긴다.

## D09. 카르마별 기본 최종전과 엔딩
- **Chosen**: 선·중립 루트의 최종 적은 악마가 빙의한 공주다. 공주를 물리치면 선 루트에서는 주인공의 선한 에너지로 정화하고, 중립 루트에서는 공주가 사망한다. 악 루트에서는 왕과 병사들이 최종 적이며, 승리한 주인공은 마왕의 힘을 받아들여 새로운 마왕이 된다.
- **Rationale**: 하나의 공주 보스전도 카르마에 따라 다른 결말을 주고, 악 루트는 후속 캐릭터 해금과 연결한다.

## D10. 특수 보스 범위
- **Chosen**: 첫 버전에는 카르마별 기본 보스만 넣는다. 특정 이벤트와 선택으로 기본 분기를 대체하는 특수 보스는 이후 추가할 수 있도록 여지를 둔다. 후속 보스에는 이벤트 조건과 카르마 조건을 결합할 수 있다.
- **Rationale**: 첫 챕터의 분량을 관리하면서 이벤트 기반 분기를 확장 가능하게 한다.

## D11. 캐릭터와 무기
- **Chosen**:
  - 용사: 기본 캐릭터. 검 자동 공격, 초보자용. 맷집·반사 피해 강화와 검 범위·피해·검기 강화.
  - 궁수: 첫 플레이 종료 후 해금. 활 자동 공격. 피해·관통·사거리·화상 강화.
  - 마법사: 첫 클리어 후 해금. 파이어볼 자동 공격과 지속 피해. 아이스 스피어·썬더 등 마법을 추가하며, 마법마다 투사체·장판·복제·피해 등 별도 강화 요소를 둔다.
  - 히든 상인: 누적 골드 기준으로 해금. 기본 3발의 산탄형 골드 공격. 탄환 수·피해·사거리·집탄율 강화.
  - 마왕(용사): 악 루트 클리어 해금 캐릭터로 후속 추가 예정이며 첫 버전 범위에서는 제외한다.
- **Rationale**: 캐릭터별 공격 방식과 강화 방향을 구분해 반복 플레이 이유를 만든다. 수치와 밸런스는 후속 조정이 가능해야 한다.

## D12. 판 안 성장과 영구 성장
- **Chosen**: 몬스터가 경험치와 골드를 준다. 경험치는 판 안에서만 유지되고 레벨업에 사용한다. 레벨업 때 게임을 멈추고 무작위 강화 3개 중 하나를 고른다. 골드는 패배·클리어와 관계없이 판이 끝나면 계정에 누적되어 영구 능력치 강화와 캐릭터 해금에 사용한다. 기본 능력치 강화는 비용이 오르는 단계형이며 최대 단계가 있다. 일부 패시브는 별도 해금으로 제공한다.
- **Rationale**: 판 안의 즉시 성장과 판 사이의 장기 성장을 나누고, 패배해도 반복 플레이의 보상을 남긴다.

## D13. 로그인과 계정 접근
- **Chosen**: Azure Entra ID 로그인이 필수다. DEX 직원 전용 Entra 보안 그룹의 구성원만 입장할 수 있게 제한한다. 랭킹에는 Entra 계정 표시 이름을 사용한다.
- **Rationale**: 사내 계정으로 사용자를 식별하면서 DEX 직원으로 접근 대상을 좁힌다.

## D14. 서버 저장과 네트워크 장애
- **Chosen**: 계정 진행 데이터는 Azure Functions API와 Cosmos DB에 저장한다. 진행 판은 계정당 하나만 보관한다. 자동 저장은 30초마다 및 이벤트 선택·준보스 처치 후 수행하고, 수동 저장도 제공한다. 저장 판이 있으면 이어하기/새 게임을 선택한다. 새 게임이 기존 저장을 덮어쓸 때 확인한다. 네트워크나 저장 API가 끊기면 판을 임시 저장하고 일시 정지하며, 복구 후 저장 지점부터 재개한다.
- **Rationale**: 기기 간 진행 동기화를 지원하고, 연결 장애나 브라우저 종료로 진행을 잃지 않도록 한다.

## D15. 랭킹
- **Chosen**: 점수 랭킹과 캐릭터·카르마별 클리어 랭킹을 모두 제공한다. 점수는 처치 수·진행도·보스 결과를 합산하는 방식으로 한다. 각 직원의 랭킹별 최고 기록을 서버에 저장하고, 화면에는 각 랭킹의 상위 10명만 공개한다. 10위 밖 사용자는 본인 순위만 확인한다. 전체 순위표 확장은 추후 검토한다.
- **Rationale**: 전체 직원 간 경쟁과 캐릭터·엔딩별 성취를 모두 보여주되, 기본 화면을 간결하게 유지한다.

## D16. 코드베이스 확인 결과
- **Chosen**: 기존 앱 코드·패키지 설정이 없으므로 새 앱 구성을 계획 단계에서 정한다. React·Phaser와 Azure Functions·Cosmos DB는 사용자 결정이다. React 정적 호스팅 서비스, 프론트엔드 로그인 라이브러리, API 런타임 및 데이터 문서 스키마는 구현 설계에서 Azure 환경에 맞춰 구체화한다.
- **Rationale**: 저장소는 Project Memory Starter Kit 형태이며 현재 게임 코드가 없다. 기술 세부를 기존 관례로 오인하지 않는다.

## 구현 설계에서 수치 조정할 항목
- 상인 해금 골드 기준, 몬스터·무기·보스 수치, 부활 대기/무적 시간, 경험치 곡선, 영구 강화 비용과 최대 단계, 점수 산식, 이벤트 문구·선택 결과 값은 플레이 테스트를 거쳐 조정한다.
- 보스 공격 패턴과 스프라이트 제작 방식은 계획 단계에서 작업 단위로 구체화한다.

## 기술·보안 검토 메모
- 브라우저에서 받은 점수·골드·해금 값은 그대로 신뢰하지 말고, API에서 Entra 토큰과 DEX 직원 그룹 소속을 확인해야 한다. 랭킹·영구 보상 제출의 검증 방식은 계획에서 구체화한다.
- 연결 장애 중 브라우저에 보관하는 임시 진행 상태는 임시 저장이므로, 서버 동기화 성공 여부와 충돌 처리 방식을 구현 계획에서 정한다.
- Entra 보안 그룹 ID, 테넌트/앱 등록 값, Azure 리소스 준비 여부는 저장소에서 찾을 수 없다. 실제 배포 설정 시 회사 담당 값이 필요하다.
- 현재 저장소는 Git 저장소가 아니며 `package.json`과 앱 소스가 없다. 따라서 이번 단계에서는 파일 기반 결정만 저장하며 코드나 커밋은 만들지 않는다.
